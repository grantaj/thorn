# Local Lean replay opportunity evaluation

Issue: #115  
Disposition: **NARROW**

## Question

This evaluation asks a deliberately narrower question than general automatic
formalisation:

> **Can Thorn recover enough precise local semantics from ordinary mathematical
> LaTeX to generate useful Lean-checkable proof commitments without guessing or
> requiring Lean-oriented authoring?**

Lean is the fixed evaluation instrument here. This tranche does not compare
solvers, add theorem search, synthesize tactics, or broaden the Lean language.
The main object under test is the **input Thorn can honestly hand to Lean**.

This is also not a formalisation-coverage experiment. A proof can contain deep
informal regions and still contain valuable local operations such as applying a
previous result, instantiating a quantifier, rewriting by an equality, or using a
hypothesis in scope. The desired product signal is source-linked evidence about
such an operation, not a percentage of a paper translated to Lean.

## Reproducibility and execution boundary

The public mechanical inventory is generated by:

```bash
python scripts/measure_lean_replay_opportunity.py \
  --thorn-revision "$(git rev-parse HEAD)" \
  --output /tmp/lean-replay-opportunity.json
```

The normal run uses Thorn's local spaCy frontend and makes **no provider/model
calls**. Ordinary CI also runs a degraded `--structural-only` smoke pass. The
Local NLP contract runs the normal inventory and uploads the JSON as a workflow
artifact.

The public corpus is frozen in `eval/lean-replay-opportunity-public.json`. The
mechanical run that established the classifications below used the normal local
NLP pipeline on PR #118. The branch changes no `src/thorn` semantic code: it adds
only the evaluation harness, manifest, workflow exercise, and this report. The
canonical behaviour under test was the public `main` implementation at the start
of the tranche (`6c32edb510bf1da560304107e54d15b494b40ca1`) plus the evaluation
files; the PR is rebased/validated against current `main` before merge.

The public run completed keylessly with the normal CI, Local NLP contract, and
Lean contract all green.

### Private natural-paper lane

The held-out lane uses six existing reduced real-paper/control proof units in
`thorn-private`, arranged as three defect/control pairs across three mathematical
families. Private source is not copied into this repository.

The GitHub integration used for this tranche can read that corpus but cannot
create a private branch or dispatch a new private workflow. The private
classifications therefore use:

- direct inspection of the already-versioned six reduced units; and
- the most recent keyless private real-paper acceptance pass, which tested the
  post-#83 structural stack at public revision
  `ba731c1d508d059a69aaecd43ece456bd7e6ac0b` and explicitly records the
  remaining application/transformation gaps.

Later public changes before #115 were review protocol/report/visualisation,
onboarding/CLI, and documentation work rather than a new semantic-transformation
backend. The private evidence is used qualitatively and is kept separate from the
current public mechanical counts rather than pretending it was freshly executed
by this PR.

## Corpus

The product-opportunity corpus contains **12 ordinary proof units across at least
six mathematical families/domains**:

- six public ordinary/user-facing units:
  - elementary arithmetic (three units in the quickstart paper);
  - real algebra (the quickstart cancellation defect and a square-bound proof);
  - elementary real analysis (a monotone-limit proof);
- six held-out private reduced units:
  - a matrix/spectral threshold pair;
  - an optimisation/contraction pair;
  - a nonlinear convergence/stability pair.

Two additional synthetic theorem-application fixtures are retained **only as
backend calibration**. They are not counted as evidence that the operation occurs
naturally.

The private pairs were selected before looking at #115 outcomes; they are the
existing held-out bad/control regression material rather than cases manufactured
for Lean.

## Classification

The required classes are:

- **A — replayable now:** canonical state fixes the exact local operation strongly
  enough for meaningful independent replay;
- **B — bounded generic capability missing:** canonical state already fixes the
  mathematics, but a specific generic Lean/lowering capability is missing;
- **C — harmless human-to-formal context:** the move is clear but formalisation
  needs ambient plumbing that is not a paper concern;
- **D — genuinely outside current mechanical recovery:** substantive reasoning is
  not represented precisely enough and should not be guessed merely for coverage;
- **E — Thorn recovery/fidelity gap:** the source makes a sufficiently clear local
  commitment, but Thorn loses, downgrades, or fails to mechanically reach that
  commitment before the Lean boundary.

That means the next bottleneck is not “support more Lean”.

## The most informative public case: the quickstart transfer

The public clean quickstart is especially useful because its final theorem is the
kind of proof island #115 hoped to find:

```text
deep/unsupported proof of lemma 1
    -> use lemma 1 to obtain E(2)

deep/unsupported proof of lemma 2
    -> use lemma 2 at x = 2, requiring E(2), to obtain S(2)
```

On the normal local-NLP inventory Thorn recovers two `result_application`
transformations. For the second it also recovers:

- the referenced result;
- the target proposition;
- a confident parameter binding (`x := 2`);
- the expected application precondition;
- a discharged local match for that precondition.

This is almost exactly the desired Lean input.

However, both result support atoms are `ambiguous`, and therefore both
transformations remain `ambiguous`. `project_lean()` refuses the theorem with:

```text
ambiguous semantic transformations are never selected for Lean proof terms
```

That refusal is correct: Lean lowering must not upgrade ambiguous canonical
semantics merely to make a proof compile.

The source of the ambiguity is upstream. When the local linguistic frontend is
enabled, `apply_linguistic_uncertainty()` treats result-reference support as a
cue-only relation and downgrades an otherwise confident support edge to
`ambiguous`/`unresolved` because support versus exposition is not generally safe
to infer from a familiar reference alone.

That conservative rule is valuable in the general case. The #115 result is that
it is currently too coarse for an explicitly proof-operational sentence such as
“By Lemma X, ...” where source structure, the cited result, target proposition,
and application matching together may provide stronger evidence than the cue
alone.

### Product inconsistency exposed by the evaluation

The quickstart documentation currently tells a user to run normal:

```bash
thorn lean examples/quickstart/clean/paper.tex \
  --result thm:main --output .thorn/quickstart-main.lean
```

and says the example reports `Status: complete`.

The normal local-NLP #115 run instead reports the equivalent canonical state as
unsupported for the ambiguity above. The existing quickstart Lean smoke test
passes `--structural-only`, which bypasses the linguistic downgrade and therefore
masked the discrepancy.

This is a first-run product defect discovered by #115. It should be repaired at
the owning support/recovery boundary rather than by teaching the Lean renderer to
ignore uncertainty.

## Backend calibration: the Lean boundary itself has useful signal

The two synthetic #77 theorem-application fixtures answer a different question:
**if Thorn does generate sufficiently precise input, is the current Lean boundary
useful?**

On the structural/canonical calibration path:

### Positive control — A / usefulness class 1

Thorn fixes an exact application of a universally quantified result, fixes the
instantiation, finds the required premise in local context, emits a complete
hole-free Lean theorem, and the pinned Lean executable accepts it.

This is genuine independent support for the recovered author-claimed transition.

### Missing-premise control — A-shaped conflict / usefulness class 2

The paired fixture changes the available premise. Thorn still identifies the
same result application and expected precondition but cannot discharge it. The
semantic application obligation remains unresolved and the exporter emits an
explicit source-linked formalisation obligation/`sorry`, classifies the result
`partial`, and never calls it mechanically checked.

This is the right discrimination: the system does not invent the missing premise
and does not claim Lean acceptance.

The normal local-NLP pipeline currently downgrades the result supports in these
fixtures too, so they become E at the product input boundary. That does not erase
the backend calibration; it locates the problem earlier.

## Defect/control signal in ordinary material

The held-out pairs provide a useful contrast with the synthetic calibration.

### Nonlinear stability pair

This is the strongest natural candidate for exact theorem-application replay.
The control says, in ordinary prose, that the current hypotheses exactly match a
known decreasing-limit stability result and applies it. The defect has only an
`L^1` subsequence before invoking the same decreasing-limit result.

Private acceptance shows that the mismatch is now review-reachable, which is a
real improvement. But it is still not lowered as an imported result with an
explicit precondition that can be replayed independently in Lean. Thus a highly
promising proof nugget exists in the source, but Thorn does **not yet generate the
formal input** for it.

### Matrix threshold pair

The defect/control distinction lives in a precise threshold expression and the
subsequent substitution/sign argument. Private acceptance improved exact source
reachability on the natural-size paper, but the reduced path exposed a general
multi-clause definition-extraction gap and neither side became a precise local
rewrite/application for Lean.

### Optimisation/contraction pair

The defect asserts a mathematically invalid promotion from two-sided function
value growth to stronger derivative/curvature properties; the control assumes
those stronger properties explicitly. The private review boundary can challenge
more of this than earlier versions, but the proof operation is not represented as
an exact typed implication/rewrite suitable for independent replay.

These pairs therefore reinforce the public result: there are **useful potential
nuggets in ordinary mathematics**, but the limiting step is currently semantic
recovery into canonical local operations, not Lean elaboration.

## Mixed-proof requirement

The clean quickstart gives a concrete mixed-proof result.

The proofs of `lem:even-two` and `lem:even-square` are themselves outside the
current mechanically recoverable Lean subset. Nevertheless, their **statements**
and the final theorem's local applications are enough for the structural-only
backend to prove the final transfer theorem from those imported statements.

This demonstrates that whole-paper or whole-proof formalisation is not necessary
in principle: unsupported neighbouring mathematics can coexist with a useful
local formal check.

The normal pipeline currently loses that opportunity because the application
support is ambiguous. Therefore the proof-island architecture remains plausible,
but current Thorn does not yet expose it reliably to the product path.

## Harmless formalisation context (#98 boundary)

No ordinary candidate in this tranche reached class C. That is itself useful:
none of the observed blockers was merely a Lean typeclass/elaboration nuisance
after an otherwise exact local operation had been fixed.

Several proofs would of course require real-number, matrix, topology, or operator
structure before full formalisation. This evaluation does **not** reclassify those
ambient requirements as paper defects. The #98 materiality policy remains the
authority for distinguishing harmless implicit mathematical background from a
load-bearing missing assumption.

Because the current cases fail earlier, adding ambient Lean declarations now
would be premature and could easily launder semantics Thorn has not actually
recovered.

## What was not observed

The experiment found no recurring ordinary B family. In particular it does not
currently justify opening speculative Lean issues for:

- abstract-domain lowering;
- equality rewriting;
- witness introduction;
- broader real algebra;
- Mathlib integration;
- generic tactic synthesis.

Some of these may become valuable later. #115 does not provide the evidence for
them yet.

Likewise, failure of the ordinary cases is **not** evidence that Lean is the wrong
checker. Most cases never supplied Lean with a semantically fixed operation to
check.

## Disposition: NARROW

The result is **NARROW**, with an explicit sequencing constraint.

### What survives

Keep the Lean bridge for the bounded family already demonstrated by #77:
mechanically fixed theorem/result application and precondition checking. The
calibration shows that this can provide both:

1. useful independent support for an exact recovered transition; and
2. an actionable missing-precondition distinction without inventing a proof.

The mixed-proof quickstart also demonstrates the architectural value of local
proof islands: the cited lemmas' internal proofs need not themselves be
formalised for their exact application to be checkable.

### What does not yet survive

Do **not** expand the Lean backend merely to increase formalisation coverage.
Across the ordinary corpus there were zero A/B product candidates in the normal
pipeline. The dominant class was E: potentially useful source commitments fail
to become sufficiently confident canonical local operations.

The immediate question is therefore upstream:

> Can Thorn distinguish an explicitly author-claimed proof use from a merely
> mentioned/expository reference strongly enough to make the former a confident,
> source-linked result application when the proposition/application structure also
> matches?

That should be tested without weakening the conservative treatment of genuinely
ambiguous references.

### Sequencing rule

1. Repair/evaluate the explicit proof-citation recovery boundary with paired
   positive/expository controls.
2. Re-run this **same frozen #115 public manifest** through the normal local-NLP
   harness.
3. Only if ordinary A/B candidates emerge should new Lean capability issues be
   opened, and only for recurring B operation families actually observed.

This is intentionally narrower than `GO`, but it is not a rejection of Lean.
Lean has passed the part of the experiment it could actually be asked to perform;
Thorn has not yet shown that its normal input pipeline can feed it useful nuggets
reliably enough to justify broadening the backend.

## Bottom line

The experiment answers the clarified product question directly:

> **Can Thorn currently generate useful input for Lean from ordinary LaTeX?**

**Not reliably on the normal product path yet.**

It can already generate a useful exact theorem-application check when canonical
support is mechanically confident, and that check has meaningful positive and
missing-premise signal. But ordinary proof material in this tranche is blocked
mostly before the Lean boundary, especially by incomplete or deliberately
ambiguous recovery of the author-claimed local operation.

The next evidence-driven move is therefore to improve **proof-nugget recovery**,
not to make Lean understand more mathematics.
